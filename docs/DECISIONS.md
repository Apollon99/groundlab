implementation, needs project-owner and/or ChatGPT review), **Open** (not decided).

Review record: on 2026-11-12 the project owner reported that ChatGPT reviewed the M1 *summary* only. ChatGPT
has not inspected the repository, code, tests or HANDOFF.md. No entry below has been reviewed by
ChatGPT at code level.

| D-018 | RRF uses each arm's available ranked list as is. If BM25 returns fewer than 100 hits, only those enter fusion; no padding with artificial or zero-score documents | Approved 2026-11-12 | Implementation in M3 |
| D-019 | One canonical document text for dense retrieval and reranking (and BM25): `title + SEP + text`, empty title gives `text` alone. Text normalization, separator, truncation and tokenization settings are frozen before any confirmatory run | Approved 2026-11-12 | Values in D-019a |
| D-019a | `SEP = "\n"`; no further normalization (BEIR text as stored, no lowercasing for neural models); bge-small 512 tokens with right (end) truncation; cross-encoder input `(query, document_text)`, 512-token limit verified with the pinned tokenizer, only the document is truncated (tested), and an explicit error is raised if the query plus special tokens exhausts the budget | Approved 2026-11-12 (project owner, as written) | A newline is an explicit, stored separator that adds no vocabulary tokens; WordPiece treats it as a word boundary, so models see the same tokens as the common BEIR `title + " " + text` join |
| D-020 | BGE v1.5 query instruction policy: prepend the fixed string `"Represent this sentence for searching relevant passages: "` to every query; no instruction on documents. Set explicitly in config and recorded in manifests, never taken from a library default. Not compared or changed based on dev results | Approved 2026-11-12 (project owner: dense queries only, text in config, not changed based on dev results) | This is BAAI's documented instruction for short-query-to-passage retrieval with bge v1.5. The model card says v1.5 also works without it with a small drop, but choosing between the two on dev would be tuning, so one policy is fixed a priori |
| D-021 | Dense search: exact dot product over **all** documents, computed on CPU in float64 from the cached float32 unit vectors; ranked by score descending then doc ID ascending; every query gets exactly `depth` hits | Proposed | Exact (no ANN), deterministic, and cheap at this corpus size (5,183 x 384). GPU is used only for encoding, as in D-001 |
| D-022 | Encoder numerics: FP32 weights and activations, TF32 disabled (`allow_tf32 = False`, matmul precision "highest"), `attn_implementation = "eager"`, padding to the longest sequence per batch, document batch size 64, query batch size 64 | Proposed | Makes "FP32" literal and avoids kernel-dependent attention paths. Observed: two independent builds produced byte-identical `embeddings.npy`, and a repeated dev run produced an identical `run.trec` (same machine, driver and versions). No cross-machine bit-identity is claimed |
| D-023 | Model files are pinned per file by SHA-256 (verified against HF LFS SHA-256 / git blob SHA-1 at pinning time) and verified before every load; `groundlab models fetch [--verify-only]`. M2 pins the cross-encoder tokenizer only; its weights are pinned in M3 | Proposed | Same integrity standard as datasets |
| D-024 | Latency protocol for dense: single query end to end (tokenize, encode on GPU, exact search, rank top-100), 10 untimed warm-up queries, each dev query timed once with CUDA synchronized; report mean, p50, p90, p99, min, max. The evaluated run comes from the batched pass, not the latency pass. GPU memory = PyTorch peak allocated/reserved (excludes the CUDA context) | Proposed | Simple and defensible; separates throughput (batched) from per-query latency |
| D-025 | Tests that need the real pinned model files are marked `pinned_models` and skip with an explicit reason if the files are absent; they never download. CUDA tests are marked `cuda`. Dense logic is otherwise tested offline with a tiny locally generated BERT | Proposed | Keeps the suite runnable offline without hiding what was not run (pytest `-rs` lists skips) |
| D-026 | BM25 index files are not byte-reproducible across builds: bm25s assigns vocabulary IDs in Python set order, which depends on hash randomization. Scores and rankings are unaffected (dev `run.trec` byte-identical across rebuilds) and index integrity is checked against the hashes recorded at build time | Proposed (documented limitation) | Could be removed by fixing `PYTHONHASHSEED`; not needed for correctness |
| D-027 | MiniLM cross-encoder weights are pinned: `model.safetensors` (90,870,598 bytes) SHA-256 `821d1aa69520101d6e0737f78a042ae25b19e5cb9160701909d10434f4aeb0ae` (equal to the LFS SHA-256 Codex checked at the pinned revision) is added to the existing `ModelSpec`, next to the tokenizer files. The reranker loads only that file: `use_safetensors=True`, `local_files_only=True`, after per-file verification. Completes D-023 | Proposed (M3) | No pickle, no network at run time |
| D-028 | Rerank arm: raw finite logits (`num_labels == 1`, no sigmoid); FP32, TF32 off, eager (as D-022); input = raw query + canonical document text via `encode_cross_encoder_pair` (512, document-only truncation, no BGE instruction); only `min(30, len(fused))` candidates scored; head reordered by logit descending then doc ID ascending, positions after 30 unchanged; pairs of one query form one batch in chunks of 32 padded to the longest pair, never mixed across queries; run-file scores of the final list are strictly descending rank scores (logits and RRF scores are on different scales), raw logits are not stored | Proposed (M3) | Fixed, explicit numerics; the evaluated run and the timed path use the same batching policy. Limit: padding length depends on the candidate set, so logits can differ from other batchings at ~1e-6 |
| D-029 | RRF implementation (applies D-001/D-018): exact `Fraction` sums, k=60, 1-based ranks, first 100 real hits per parent, no padding, absent = 0, score descending then doc ID ascending, top 100 emitted. Config rejects any other k, depth or fusion method. Parents are reused through their own configs and verified indexes; their ranking code is not modified. Hybrid and rerank configs of a view name identical parents and fusion settings (tested), and each manifest records `fused_candidates_sha256` | Proposed (M3) | Exact arithmetic removes float-ulp ties between mathematically equal scores. Stored float scores may repeat; ranks decide |
| D-030 | Fused-arm measurement: throughput pass (all queries, per-phase seconds, per-phase CUDA peaks read before the next reset) and a separate timed single-query pass over the full pipeline (10 untimed warm-up queries, each query timed once, mean/p50/p90/p99/min/max overall and per phase, one outer peak probe). `build` of a fused config only verifies parent indexes and reranker files and requires CUDA; test split is refused before data or model access | Proposed (M3) | Same protocol as D-024 extended to the whole pipeline. Single timing per query on one occasion; GPU clocks are not controlled |
| D-031 | Fixed primary contrasts: dense vs BM25, hybrid vs dense, and rerank vs hybrid. Two-sided cluster sign flips, Holm across three, 95% paired cluster-bootstrap intervals | Frozen before held-out scoring | Dense is the fixed semantic comparator. Dev summaries were visible at the decision |
| D-032 | +0.02 nDCG@10 is descriptive. Report zero-null results, effect direction, and whether the point estimate reaches +0.02 | Frozen before held-out scoring | Synthetic margin checks are exploratory |
| D-033 | Freeze binds prepared-data manifest and analysis protocol alongside effective arm config, code tree and uv.lock. Raw held-out artifacts remain local under ignored outputs | Frozen before held-out scoring | Integrity and dataset terms |
| D-034 | Shared warmed single-query protocol, ten warm-up queries and one timing per query. Four OMP/MKL/OpenBLAS threads in the held-out runner | Frozen before held-out scoring | p50/p90/p99 and GPU memory are hardware-specific |
